3 用户每天得到什么

系统提供一个固定入口 report/latest.html，并保留每个交易日和运行版本的历史报告。用户无需逐个执行几十个脚本。

场景 用户动作 系统动作
模拟盘普通日 晚上看日报；状态正常且无待办即可结束 更新数据、结算此前模拟订单、更新估值/权益、对账、报告、备份
模拟盘调仓周期 查看新目标及订单原因；默认规则已登记则由模拟器处理后续成交 月末盘后形成次日起生效的目标，按日期推进，保留部分成交和偏差

金额用 Decimal 计算并按明确精度持久化，现金舍入与证券 tick 分开；数量以股/份计。时间戳带时区，交易日按 Asia/Shanghai 日历。接口及数据都带 schema_version。

行情标准表包括证券版本/代码映射、交易日历、未复权日线、复权因子、历史状态及涨跌停、公司行动、历史股票池和来源记录。账本包括计划、订单、成交、资金事件、公司行动事件、持仓批次、风险、导入批次、对账和作业状态。

历史快照不可覆盖；清洗新版本与源修订产生新快照。信号只能看到决策时点已允许看到的数据；冻结不等于证明历史数据没有修订。历史回补的可用时间推定与真实首次观测必须区分。

研究价格可做复权，成交与账本用未复权价格加真实公司行动，不重复计分红。缺 bar 必须区分停牌、未上市、退市、休市和源缺失；禁止无条件填充后当可成交行情。

数据供应商失败时不静默换源；新增供应商或数据库先过相同契约测试。费用、时间、状态或单位变更必须使缓存失效。

6 策略成交与账户时序

ETF 示例：预登记候选池；月末盘后，用当时可见的 120 个交易日收益选正收益前二，每只 paper 目标最多 20%，不足部分留现金。

个股示例：历史沪深主板可投资范围，排除当时 ST/退市整理及上市不足 252 个交易日者；过去 20 日成交额中位数前 300 中，按 60 日收益波动从低到高取五只，每只 paper 目标最多 8%。历史包括后来退市的股票；不足窗口不得补未来数据。

统一时序：

  1. D 日已完成的市场与账户事实先入账并核对，再在盘后形成新目标。
  2. 新目标最早 D+1 生效，不能回头成交在 D 日。
  3. 日线回测和 paper 使用登记的次日收盘附近价格代理；真实人工执行示例窗口为 14:50–14:56，二者不视为精确相同。
  4. 执行数量从已知参考价与账户确定，未来成交价不能反向改变此前选股。
  5. 买入预算不复用当天卖出资金；次日对账后再产生剩余买单。这是首版保守执行政策。
  6. 日内订单仅当日有效；目标可在最多三个交易日的 paper 示例有效期内继续尝试。每次先终结/核对旧订单，再根据真实状态生成新 intent。
  7. 期满、用户错过窗口或计划被替代时，旧订单不得直接复用；保留未完成原因。

RQAlpha 的有效配置和代码行为都必须验证；1d 的 next_bar 参数不自动保证次日成交，默认股利税和退市处理不能直接当真实账户结果。具体固定版本来源和适配要求见详细实现规格。

7 持续模拟与人工执行

模拟盘使用独立 paper 账户及数据到达记录。优先验证引擎检查点恢复；不支持可靠续跑时，重放已冻结逐日输入和订单，逐项比对历史事件前缀，仅追加新事件。既有事件不因后来数据修订或策略升级被覆盖。

跨日顺序在事件层明确：根据交易日历解锁可卖数量、处理当日适用公司行动，再处理订单和成交，随后按时点估值。若外部信息晚到，按原事件时点重新核对相关计算，保留修订证据；有影响且未解释时阻断新计划。不能只按文件到达顺序生硬更新。

人工清单输出 plan.json、plan.csv、plan.html。导出只代表 EXPORTED，手工提交后登记 SUBMITTED；未知是否提交用 UNKNOWN。撤单请求不是撤单成功，部分成交、晚到成交和费用必须处理。

导入四类记录：委托、成交、资金流水、账户快照。先 preview 校验，按 batch 原子 apply；用符合券商编号作用域的业务键跨文件去重。没有稳定 ID 的歧义需明确处理，不能把两笔相同价格数量的成交误合并。

成交入账、事件去重、账户投影处于同一数据库事务。对账比较订单/成交、现金流水、账户快照；来源事实优先，差异不能靠伪造交易凑平。真实账户需要初始现金/持仓/批次和待处理权益；缺失时标记未知并保守预留。

8 风控与可操作状态

无论使用哪种策略、数据库或 harness，必须保留：资金与可卖约束、交易单位和价格合法性、过期/重复/未知订单阻断、关键数据完整性、账户核对。

日报显示彼此独立的状态，不把“数据正常”写成“可以下单”：

字段 允许的关键状态
job_status SUCCESS、PARTIAL、WAITING_DATA、FAILED、NOOP_MARKET_CLOSED
data_status READY、STALE、INCOMPLETE
reconciliation MATCHED、PENDING、MISMATCH
risk_state RUNNING、REVIEW、HALTED
plan_state NONE、DRAFT、RISK_PASSED、EXPORTED、SUPERSEDED、EXPIRED

只有对应任务、数据、账户、风险与当日计划都满足要求，manual 计划才能输出“执行前检查通过”。它不是成交保证，执行前仍核对券商最新行情与账户。

暂停跨重启保留。恢复须修复原因、核对账户与订单、更新数据、作废旧计划并记录操作人及原因。允许导入、读取和核对；禁止按坏数据盲目清仓。风险减少订单也要检查数量、价格与可卖，不获得绕过账本的特权。

9 日常入口和失败语义

下面是待实现命令协议，当前不可运行。高层命令应调用已经定义的低层数据、计划、导入和对账功能，不产生第二套业务逻辑。

uv run ashare status --account paper
uv run ashare daily run --account paper --date YYYY-MM-DD
uv run ashare report daily --account paper --date YYYY-MM-DD

uv run ashare status --account manual
uv run ashare plan preflight --plan PLAN_ID
uv run ashare plan export --plan PLAN_ID
uv run ashare order register --intent INTENT_ID --broker-order-id BROKER_ID
uv run ashare import preview --account manual --mapping configs/brokers/manual_csv.yaml --file FILE

uv run ashare reconcile --account manual --date YYYY-MM-DD
uv run ashare daily run --account manual --date YYYY-MM-DD

daily run 先解析账户模式和交易日，拿锁并恢复未完成批次；获取当天输入，按事件顺序更新当前账户并核对，最后才生成未来目标和计划，再报告与备份。paper step 是同一编排在 paper 模式下的兼容入口，不能另做一套 daily 逻辑。

状态输出必须写明截至哪一交易日。昨天成功的页面不能在今天任务缺失时继续显示“今天正常”。数据或交割单未齐返回 WAITING/PENDING，报告继续生成但无新的可执行计划；重试不能重复入账。作业运行中断用持久 checkpoint/批次登记恢复，不自动重发未知订单。

休市日返回 NOOP_MARKET_CLOSED，允许核对、备份和研究。禁止把当前墙上日期当作交易所开市证据。启动有副作用的模拟/人工计划阶段前校验时间；不能把收盘后才出现的计划倒填为收盘前订单。

3 普通模拟日的最短操作

正常配置调度后，你打开日报，按下面顺序查看：

  1. 日期正确吗？显示的 latest 可能仍是昨日页面，必须查看“预期交易日”和“最新成功运行日”。
  2. 数据齐全吗？关键行情、交易状态、分红等是否 READY。
  3. 账户正常吗？模拟引擎与独立账本是否 MATCHED，有无未知事件。
  4. 风险正常吗？RUNNING、REVIEW 还是 HALTED；有无需要处理的原因。
  5. 今天发生了什么？成交、费用、股利、持仓变化和资产估值是否有解释。
  6. 明天需要做什么？没有调仓及未结事项时明确显示“无需交易操作”。

全部正常且无待办即可结束。无需每日手动导入虚拟成交，也无需重新从第一天跑一次策略搜索。如果未启用调度，手动执行同一高层入口：

uv run ashare daily run --account paper --date YYYY-MM-DD
uv run ashare status --account paper
uv run ashare report daily --account paper --date YYYY-MM-DD

这些命令待实现。daily run 必须幂等；如果结果是 WAITING_DATA 或 FAILED，不能因为命令结束就视为今日已完成。重复运行用于恢复，不重置资金或重新挑选昨天的参数。

4 月末与下一交易日怎么衔接

令 D 为当月最后一个交易日，D+1 和 D+2 表示后续交易日，不是自然日。

日期 实际顺序
D 盘后 先完成 D 的旧订单、权益、估值与对账，再运行月度策略，生成新目标和次日起有效的草案
D+1 执行前 结合最新账户和状态复核，过期或被替代的草案不得使用
D+1 paper 模拟既有订单；manual 由你提交通过检查的订单，记录部分成交或拒单
D+1 盘后 按真实/模拟成交更新账户，未成交状态核清，对账后再计算剩余目标
D+2 及目标有效期内 前一天卖出释放且已核对的资金可以支持后续买单；旧订单终态确认后才生成新 intent
目标期满 未完成部分失效并列出原因，不无限追价，等待新的显式决策

首版买单不使用当天卖出的资金，所以一次换仓可能分两天或更多天完成。这是可配置但需前后一致的工程政策。若改成当天卖出后接着买，必须同时改变模拟成交顺序、人工操作和验收，不能只改一个仓位公式。

有计划并不表示今天一定成交；也可能因价格保护、资金、交易限制或未知状态而全部不执行。月末不在交易日时按日历定位实际 D；节假日不生成假交易。

5 人工执行日的操作清单

5.1 打开计划并核对

确认模式为 manual、账户正确、有效交易日是今天、plan_id 是最新版本。检查标的代码/名称、买卖方向、当前/目标/可卖数量、价格保护、费用和剩余现金。只使用通过执行前检查的清单。

最新账户证据包括持仓与现金；待成交委托也会占用资源。当天无交易仍应有带时点的账户/订单证据或人工确认记录，不能反复导入旧文件就假装今天核对通过。人工确认的证据等级要标明。

5.2 执行前检查并提交

uv run ashare plan preflight --plan PLAN_ID
uv run ashare plan export --plan PLAN_ID

在券商软件核对最新报价、可用资金、可卖数量与未成交委托。没有实时 API 时，由你记录检查时刻和参考值；系统不能显示“已自动实时验证”。

按清单提交限价委托，登记对应 intent_id 和券商委托号。没有拿到委托号但可能已经点击提交的，记为 UNKNOWN 并查询券商，不再提交一个相同订单。

uv run ashare order register --intent INTENT_ID --broker-order-id BROKER_ID

数量、标的或价格保护之外的调整需要重新规划和检查，不直接篡改清单后当成原计划执行。你在券商软件进行的计划外交易仍需导入，记录 EXTERNAL 并重新核对账户。

5.3 收盘后导入与核对

按实际券商文件格式导出委托、成交、资金流水和持仓/现金快照，可逐类导入。先预览，确认错误行、重复记录和预计账户变化，再提交：

uv run ashare import preview --account manual --mapping configs/brokers/manual_csv.yaml --file FILE
uv run ashare import apply --batch BATCH_ID
uv run ashare reconcile --account manual --date YYYY-MM-DD
uv run ashare daily run --account manual --date YYYY-MM-DD

看到“无新增成交”不能推断委托已撤销；仍需核对未成交订单。部分成交只按成交数量入账。费用和交割单晚到时保留 PENDING，次日补齐并调整，不能凭空填写零费用。

检查现金、持仓、可卖和未完成订单差异。报告为 MATCHED 且没有未解释事项，才算该阶段完成；执行窗口过后不拿当天剩余旧清单在别的时间追单。

6 无交易日和非交易日怎么做

普通交易日没有调仓：系统照常更新数据、估值、权益、风险和备份；manual 用户仍核对账户变动。公司行动、计划外交易和未结订单可能产生待办，所以“没下单”不代表可以跳过账本。

交易所休市日：不发出交易任务；可以补历史数据、查看报告、做备份恢复或研究。日报/状态显示 NOOP_MARKET_CLOSED，并注明最新有效行情日，不能误报数据延迟。

周度工作：查看未结项、成本与未成交统计、数据修订、备份和运行遗漏。月度工作：审阅调仓理由、策略与基准表现、执行误差，并做恢复演练。研究新策略另开 research 运行，不直接覆盖正在使用的版本。

7 异常时具体怎么做

报告提示 用户动作 系统应做什么
数据不齐或过期 等待重试，必要时检查账号权限和源服务 显示缺哪张表/哪一天，阻断新计划；保存上次状态但标明陈旧
今日任务没有运行 检查机器休眠、调度和锁，恢复任务 补数据和报告；未预先生成的订单不能追溯成交
订单是否已提交不确定 在券商查委托/成交并补登记 保持 UNKNOWN，禁止重复或替代下单
部分成交或撤单中 查剩余委托状态，必要时手动撤单并导入确认 正确保留已成交数量；撤单请求不当作成功
现金或持仓不一致 对照原始流水、费用、股利与外部交易 列差异及证据，阻断新买单，不能自动凑平
风控暂停 看清触发原因，按登记政策核查 跨重启保留暂停，支持读取、对账和受检查的风险处置
错过执行窗口 标记未执行，核查是否存在已提交单 原订单失效；下一交易日重算，不能复用旧单
数据/策略后来修订 保留旧 paper 记录，新研究另开版本 不覆盖旧成绩；若影响账户事实，生成审计修订并重新核对
备份失败或磁盘不足 释放/恢复存储并确认备份状态 停止有风险的写入和新计划发布，保护现有事件

任何暂停的恢复顺序：修复原因 → 获取最新状态 → 对账 → 检查数据 → 作废旧计划 → 记录恢复原因 → 重新规划。重启、等待一天或直接修改数据库都不能作为恢复方式。

8 日报应该怎样呈现

首页先回答“现在需要你做什么”，然后再展示收益。至少包括：

  • 模式和账户：paper/manual，账户脱敏名称。
  • 有效日期：预期交易日、最新成功日、数据/券商文件到达时间。
  • 独立状态：任务、数据、对账、风险、计划和备份。
  • 账户：总资产、可用/冻结现金、持仓/可卖数量和应收权益。
  • 今日变化：成交、费用、分红、资金进出、未成交及未知订单。
  • 明日待办：计划编号、有效期、原因、需要人工完成的动作；无事则写明。
  • 表现：净值、回撤、基准、交易成本，注明是模拟还是实际。
  • 证据入口：数据版本、成交原件、运行日志、差异明细、备份编号。

示意文字如下，金额和状态不是本次实际运行结果：

账户：paper-demo
预期交易日：D
最新完成：D
数据：READY    对账：MATCHED    风险：RUNNING
今日新增目标：无
有效待执行订单：0
待人工处理事项：0
下一步：无需交易操作，下一交易日继续自动运行

4 模块边界和稳定契约

建议用 Python Protocol 描述边界，用 Pydantic 校验跨模块载荷，用 JSON Schema 导出外部契约。内部可用 DataFrame/Arrow，但约定主键、类型、时区、单位和排序；不得只传无规格的任意 DataFrame。

MarketDataView bars / instruments / status / actions，绑定 snapshot 与 decision_at 信号侧只返回当时允许见到的数据；禁止绕过时点过滤

关键业务对象必须包含：

  • Instrument：内部稳定 instrument_id、交易所 MIC、证券类型、币种；代码通过带有效期的映射表关联 vendor symbol 和 broker symbol，不仅保存六位字符串。
  • Snapshot：snapshot_id、schema_version、每个表的文件清单与哈希、数据区间、供应商、转换版本、质量报告、时间语义。
  • TargetPortfolio：strategy_id/version、decision_at、trade_not_before、expires_at、snapshot_id、权重和原因、建议现金比例；非调仓日返回 NO_REBALANCE，不能把空列表误作清仓。
  • OrderIntent：intent_id、plan_id、账户、标的、方向、数量、限价保护、有效日、依赖条件、费用估计、risk_result_id。
  • ExecutionEvent：event_id、账户、券商委托号/成交号、事件时间与接收时间、事件类型、数量、价格、费用、来源批次、关联 intent；未知关联不得自动猜测。
  • AccountView：现金总额、可用现金、冻结现金、可取现金（如源提供）、总持仓、可卖数量、冻结数量、应收股利、数据截止时间与核对状态。
  • ExperimentSpec：策略、数据快照、时间切分、本金、基准、规则与费率版本、撮合/滑点配置、seed、资源预算。

金额计算使用 Decimal；持久化采用明确缩放的整数或十进制字符串，禁止依靠 SQLite REAL 做账户金额。内部计算可保留至百万分之一元，现金记账按券商分币规则舍入；价格另按股票/ETF tick 校验。数量是股/份的整数；行情成交量保留源精度后验证转换误差。

所有业务时间用带时区的 timestamp；交易日用 Asia/Shanghai 日历，数据库可存 UTC 并保留 exchange_date。不能把周一至周五直接当交易日。

配置和事件都带 schema_version。兼容升级只新增可选字段；删字段或变单位必须升大版本并提供迁移。读取未知大版本直接报错，不能猜。

5.4 时间语义与质量门禁

区分 event_time（发生）、effective_time（生效）、published_at（公告）、observed_at（本系统首次取得）、available_at（评估器允许策略看见）。保留 available_at 的依据：源时间戳、保守规则或真实首次观测。

历史回补的数据在 2026 年抓取，不代表 2017 年的策略都不可见，也不代表供应商能证明当时的原始版本。研究模式可以声明“按公开日推定可用”的历史假设；严格 paper 模式以实际到达时间控制。冻结快照保证可复现，不能单独证明不存在历史修订或未来信息。 财务、历史分类等缺少旧版本时，要降低证据等级。

日线策略只读 D 日完成并验收后的数据；若没有明确发布时刻，盘后统一延迟到配置的决策时刻，如 21:30，且检测实际齐备情况。Tushare 分红接口文档写明 20–21 点更新，任务不能仅因日线已到齐就宣布全部数据可用。当日 ST 列表 09:20 更新不能在回测里假定 08:30 已知；盘前的 draft 和开盘后的最终检查必须区别。完整 bar 最早供下一交易日使用。

发布快照前检查：

  1. 分页完整、请求区间完整、主键无冲突、有效证券与日历覆盖有统计；接口返回满页不能视为全部下载完毕。
  2. OHLC 非负且区间合法；单位转换和成交额/成交量均价量级合理；字段改名、异常 NaN 直接失败。
  3. 缺失分成休市、未上市、停牌、退市、源缺漏；只有估值允许带标记沿用旧价，信号窗口和撮合不得默默前向填充。
  4. 因子跳变应能关联公司行动；涨跌停参考价不能无条件等于昨日未复权收盘价。
  5. 关键状态缺失时不输出“可执行”计划；数据不齐只能产生带阻断原因的报告。
  6. 同源重拉差异、跨源小样本差异都保留；source 优先级不可由策略自由改变。

6 策略和组合的首版规格

这两条是验证系统的研究假设，不是已经证实的赚钱策略。窗口和权重在第一次实验前登记；不要让执行 agent 自动搜索“最高 Sharpe”再把参数当默认值。

6.1 ETF 趋势示例

预先登记 3–5 只境内宽基股票 ETF 的白名单、类别与选定日期。只在其上市后且至少有 121 个有效收盘观察时使用。白名单按今天选出会有选择偏差，因此历史结果标为“固定清单的条件实验”，不声称复现当时全 ETF 市场选基效果。

每月最后交易日盘后，用截至 D 的复权研究价格计算 120 个交易日总回报代理。正回报者按回报排序，取前 2 名；每只最多分配账户 20%，不足两只时余款留现金，全部不满足则该策略目标为现金。并列按内部 ID 稳定排序。

复权序列的收益定义和供应商算法要在 manifest 中注明；这只是趋势信号，真实账户仍用未复权价格和公司行动记账。趋势研究背景见 Time Series Momentum，其研究对象并不直接验证本方案的 A 股 ETF 参数。

6.2 个股低波动示例

每月最后交易日盘后，从当日已上市至少 252 个交易日、非 ST、非退市整理的沪深主板普通 A 股中选候选，保留后来退市的证券历史。使用过去 20 个交易日人民币成交额中位数筛前 300 只，再以过去 60 个有效日收益标准差从低到高选 5 只，账户权重每只最多 8%，合计最多 40%。

日收益用经过验证的复权研究序列；60 个收益至少需要 61 个价格。首版要求对应窗口覆盖所有预期交易日；停牌/缺数据导致不足者不新买入。并列按 ID 排序。不使用当前总市值、当前行业或当下指数成分去筛历史。20/60/252/300/5 均为待检验规格。

低风险效应仅提供研究动机，例如 Betting Against Beta；低 beta、低波动和本项目长仓五股组合不是同一个策略。五只股票的集中风险会明确显示在报告里。

6.3 基准和账户合并

至少输出全现金、同一 ETF 清单固定权重、个股相同流动性股票池的等权研究组合，以及有可用数据的宽基收益参照。指数价格指数与含股息策略的口径不一致须注明；不要用一个忽略分红的指数画出“超额”。

ETF/股票各 40% 是 paper 示例，预留 20% 现金。两者在同一账户聚合、统一风控与下单；分别记录策略归因，但实际账户账本只有一套。首版不做行业硬约束，避免当前行业污染历史；输出可解释的行业集中度需先有历史分类。ETF 与个股可能重叠，未做持仓穿透时报告“穿透暴露未知”，不能宣称充分分散。

Planner 计算目标数量时使用决策时刻已知参考价，向下取整到买入单位，再按限价保护和费用重新检查现金。买不起一手就记录跳过与目标偏差，不能假设可以买碎股。可卖零股按证券规则处理。

非调仓日继续更新估值、检查风控、导入及对账。目标没有变化不等于系统当天可以不运行。

7 回测设计和必须验证的引擎行为

7.1 首版明确使用延迟到下一交易日的收盘代理

为配合日线数据和人工执行，首版研究主模型采用：D 日盘后形成不可变目标和数量草案，最早在 D+1 的日终事件提交预先生成的订单，以 D+1 收盘附近的受限成交代理撮合。人工示例执行窗口为 D+1 14:50–14:56，使用限价；这需要你届时有空，窗口可在上线前改为已登记的执行政策。

日收盘价不等于 14:50 的可成交价。 报告必须显示“日频成交代理”标签，并给出延后一个交易日、成本 2 倍/3 倍、价格不利偏移等压力结果。人工实盘记录真实执行时刻与价格，累计偏差后校准；若优势依赖几 bp 或窗口内精确成交，升级所选标的/调仓日分钟数据后再评价，不把日频结果当精确模拟。

不使用 D+1 的收盘价重新挑股、排名或增加数量。D+1 的已知状态可以阻止交易；执行日 bar 的价格和成交量仅供模拟市场判断能否成交，不能反向送入 D 日决策。策略数据视图与撮合数据视图物理隔离。

RQAlpha 当前源码会在 1d 模式把 next_bar 变为 current_bar。本设计通过“D 的计划存储，D+1 的执行回调加载”实现交易日延迟，不能只设置 next_bar。增加突变价格 fixture，断言最早成交日期严格晚于 decision_date。引擎若提前泄露 D+1 bar，验收失败。已核对源码

7.2 现金和换仓采取保守的首版政策

买入预算只用执行日前已核对的可用现金，扣掉冻结、费用和现金预留。首版不复用当天卖出产生的现金；卖出完成并在日终对账后，最早下一交易日生成剩余买入单。因此大幅换仓可能分两天完成，回测和人工计划必须使用相同政策。

这是降低人工操作和日线内成交顺序歧义的工程限制，不是把卖出款当日不可用于买入的监管规则。后续支持“卖出成交回报后解锁买单”时，只扩展执行状态机，并用分钟或真实回报验证。

未完成目标保留固定 target_id；下一日根据实际账户重算剩余差额。最多尝试 3 个交易日是 paper 示例，超时目标失效、生成偏差报告，不能无限追价。月度新目标到来时，要先处理旧计划状态并显式 supersede。

7.3 复用引擎但统一事实

实现 CanonicalRQAlphaDataSource，把证券属性、日历、bar、停牌/ST、分红送转、价格限制和可用区间全部映射到同一 snapshot。默认 bundle 可用作安装烟测，不能混入正式 run 的公司行动或日历。未实现接口显式 Unsupported，不能静默回退网络。

引擎产生订单和成交，统一转为标准事件，进入独立 Ledger。RQAlpha 的账户供仿真与下单约束使用，独立账本负责审计；逐日比较两者的经济资产、现金、持仓。发现差异必须修正 adapter/成本模型，不得仅在最终图表修一条收益曲线。

当前源码中股息税默认关闭、存在退市现金返还开关，并已有红利税和送转处理。这些是需要审阅与验证的复用点，不能推断默认即满足真实个人账户。账户实现

  • 个股红利税启用并验证持有期及分批卖出；是否对 ETF 应用由资产类别决定。
  • 禁用“退市按最后市值自动拿回现金”的假设。退市持仓转不可交易资产，基准估值按零的保守政策、回收时另记现金事件；与引擎的差异需显式适配。

7.4 成交限制和费用

日频不模拟排队优先级；在不利侧触及涨跌停时采取保守不成交政策，停牌/零量不成交。滑点后的价格不能突破订单限价、交易所价格限制或 bar 合法范围；无法满足就减少/拒绝成交，不制造 bar 外的理想成交。每日成交量参与上限与过去 20 日流动性检查都要有；前者是事后市场容量模拟，后者才是事前计划约束。不能用全天成交量证明收盘窗口存在同样流动性。

费用表按日期、账户、资产类别和方向配置。包含佣金率、最低佣金、印花税、适用过户费/规费、费用包含关系、红利税及舍入规则。最低佣金按券商实际订单收费单位汇总，不能每次部分成交重复收一份；在最终交割单到达后做费用调整事件。

股票印花税在 2023-08-28 有政策变化；红利税与持有期及卖出有关，不能在所有分红日直接统一扣 20%。ETF 的交易税费与股票分别建表。印花税公告 · 股息红利税通知

回测须输出“交易成本后净值”和“再计数据/运行固定支出的经济结果”。后者单独展示，避免固定订阅费用改变策略信号。没有实际券商费率时仅能标注情景费率，不得包装为真实账户净收益。

8 账本和公司行动

首版采用可重放的事件账本和明确的现金/证券投影，不必引入复杂会计平台。Event append、去重、现金/持仓更新必须原子提交；历史更正通过冲正/调整事件处理，不直接修改旧成交。

统一事件包括：Deposit、Withdrawal、OrderRegistered、Fill、FeeAdjusted、DividendEntitled、DividendPaid、DividendTaxPaid、SplitOrBonus、SharesUnlocked、AssetWrittenDown、CashRecovery、ExternalTrade、Correction。每个事件有来源和证据。

净资产计算为现金总额 + 可交易证券市值 + 不可交易资产估值 + 应收股利 − 已确认负债；冻结现金已经在现金总额中，不再额外相加。可用现金用于下单，不等于净资产。入金不能算策略收益，展示时间加权收益；资金使用者的实际回报可另报 XIRR。

分红至少记录登记日持仓权益、除息日应收、到账日现金转换。用未复权交易价格记账；如果同时使用复权收益再把现金分红记一遍，会重复计收益。送转要调整数量和批次成本，配股、合并换股、清算等没有适配时阻断发布相关回测结果，实际账户进入人工处理状态。

手算验收例子，均为合成数据与明确情景，不是市场报价：

情景 预期

真实持仓初始化要导入基准日完整现金与持仓，并确认尚未结算的成交、分红权益和持仓批次。拿不到历史买入日期时，红利税预测标为未知并采用保守预留；实际交割单是最终账务依据。不能为了启动方便假设已有股票都是当天买的。

9 人工执行也是完整执行系统

9.1 每个交易日的流程

  1. 导入前一日结算后的交割单和账户快照；检查未知订单与差异。未核对通过，只能生成研究信号。
  2. 拉取 D 日数据；质量门禁通过后冻结 snapshot，月末生成次日起可执行的目标。
  3. 按已核对账户生成 draft 计划。每行显示证券名/代码、当前/可卖/目标数量、买卖数量、限价保护、费用、原因、有效日和 plan_id。
  4. 执行日核对最新账户、ST/停牌/涨跌停以及价格。没有实时 API 时，人工在券商终端确认并登记检查时刻、参考价与可卖/现金；因此不能声称系统完成自动实时风控。
  5. 运行 preflight 后导出可执行清单，人工提交限价委托，登记券商委托号。报价超过保护区间、资金不足、无法确认状态时不提交该行。
  6. 导入委托状态、成交、费用、资金流水及账户快照。只有成交表无法证明“未成交委托已撤销”；相关计划必须保持待核对。
  7. 收盘后做三方核对：计划/订单、成交/资金流水、券商账户快照。生成日报、阻断项及下次需要处理的事项。

建议首版真正支持一个通用规范 CSV 和用户券商的一种导出格式；未知券商时用样例映射模板。不要一次承诺支持所有券商。

9.2 计划和订单状态机

Plan: DRAFT → RISK_PASSED → EXPORTED → RECONCILED
                       ↘ BLOCKED / EXPIRED / SUPERSEDED

Order: INTENT → EXPORTED → SUBMITTED → ACKNOWLEDGED
                                      ↓          ↓
                              PARTIALLY_FILLED → FILLED
                                      ↓
                                CANCEL_PENDING → CANCELLED
其他结果: REJECTED / EXPIRED / UNKNOWN

EXPORTED 只代表文件生成。人工已点击但没有拿到委托号，标 UNKNOWN；程序失败、空 CSV 或未看到成交不能把它改为“没下单”。UNKNOWN 阻断同一账户标的方向的替代订单，先查券商终端/当日委托与成交。

取消请求不等于已取消。允许取消期间出现新成交；最终以累计成交和实际撤销剩余量计算。终态订单收到晚到成交也要幂等入账并重新核对，不能因状态已结束就丢弃。

intent_id 由账户、target_id、有效交易日、证券、方向、执行批次确定。plan_id 绑定 snapshot、策略版本、账户状态哈希、风险版本及目标；相同输入重复生成返回同一计划。账户变更产生新版本，先显式替代旧版本。旧纸质/HTML 清单不能物理召回，所以新清单突出作废编号；操作记录是必需的。

9.3 CSV 契约和导入事务

至少支持四类载荷：orders、fills、cash_movements、account_snapshot。成交字段包括 account_id、trade_date、trade_time、exchange、symbol、side、quantity、price、gross_amount、commission、tax、other_fees、broker_order_id、broker_trade_id。计划号可缺，但缺时进入待匹配列表。

每批先校验编码（UTF-8/常见 GBK）、日期、时区、小数、买卖枚举、单位及金额一致性，再生成 dry-run 差异。批准本地导入后单事务提交；一批有关键冲突则整批不提交并输出行号，不半入账。实盘原件只保留本地且脱敏。

去重主键优先采用券商规范定义的账户 + 交易日 + 市场 + 成交编号，先确认该券商编号作用域。只有文件哈希不能防止两次导出同一成交。没有稳定编号时不能盲目按价格/数量去重，因为可能是两笔相同成交；需源行标识、委托号、时间与累计量验证并处理歧义。

计划外交易也必须记账并标 EXTERNAL，不得丢弃；无成交仅有仓位变化时记录 unexplained 差异，不能伪造一笔交易来凑平。费用晚到以 FeeAdjusted 补记。

9.4 对账的通过标准

持仓数量、可卖数量、冻结数量、委托累计成交精确一致；现金差异须按源的舍入和费用待结算分类。示例每笔 0.01 元的舍入容差只接受已解释差异，不能把“低于 10 元”设成可忽略。比较统一时刻和统一口径，券商市值与本地价格时间不同形成的差异单独展示。

报告保存来源文件、导入批次、核对时刻、差异类别、处置记录和关闭人。未解释资金/持仓差异阻断新买入。下一日计划必须从已确认真实状态重算，不能沿用理想目标持仓。

11 交易规则和实际使用前置条件

沪深交易规则均发布了 2026 修订版本，通知写明 2026-07-06 生效。上交所页面状态标签与正文曾有不一致，应结合正文、附件和暂缓条文记录版本。历史回测按历史日期应用规则，不把今天的涨跌幅和费用覆盖全历史。上交所通知 · 深交所通知

RuleSet 的选择键至少包括 date、exchange、board、asset_type、特殊状态。沪深主板普通股票与首版股票 ETF 的买入单位、价格最小变动单位、T+1 可卖和涨跌停分别验证。不要用“所有 A 股/ETF 都是 10% 或都可 T+0”的常量。即使首版不新买 ST，也要能处理持仓转 ST 后的真实限制。

程序自动生成指令也在程序化交易定义范围内，人工点击不能自动推定免报告。manual 模式实际使用前，向券商说明“系统生成买卖数量和清单，个人手动提交”，落实该账户适用的报告/核查流程，保存确认记录。证监会发布说明 · 上交所实施细则 · 深交所实施细则通知

这些是实际投入资金的入口条件，不阻碍现在完成代码、数据样本和模拟账户。用户尚未提供券商、费率、账户初始状态和个人风险预算，应在配置中标为 required，不猜测。

1 模拟盘可以怎样做

模拟盘使用虚拟资金，没有真实证券买卖。与历史回测的差别在于：历史回测可以一次计算很多年；前瞻模拟盘随现实日期推进，每天只使用那时已经得到的数据。

方式 如何运行 能验证什么 不能据此证明什么
本地日线模拟盘，首版建议 每日接新行情，前一日已确定的订单按登记规则在下一交易日模拟结算 数据更新、策略信号、账户连续性、交易限制、风控、重启恢复 日内精确成交、真实排队、券商接口质量
本地实时行情仿真 接实时行情，由本地模拟器处理虚拟订单 盘中状态、订单生命周期、部分成交/撤单流程 真实券商接受该订单或实盘必然同价成交
券商模拟账户 接入券商提供的测试环境，用虚拟资金报撤单 具体 SDK、账户、回报和查询接入 模拟环境与实盘的流动性、费用和权限完全一致
人工操作演练 对本地模拟盘的计划手工填写虚拟委托/成交 CSV 用户核对清单、导入、纠错和对账的完整操作 证券交易已发生

vn.py 的 PaperAccount 官方说明支持基于实盘行情进行本地仿真，可作为实时方案候选。是否覆盖本项目的股票/ETF 结算、分红、费用与恢复需求，仍要跑相同契约测试；模块名不能代替验收。

券商模拟账户需要确认实际券商是否提供、支持哪些品种、如何开通、指定终端和 SDK 环境。此前已读的 xtquant 文档 描述了报撤单、查询和回调；本轮重访超时，不能据此承诺你已有可用模拟账号。首版本地模拟不依赖这一步。

1.1 首版日线模拟的一天

  1. 建立独立 paper 账户，例如虚拟资金 20 万元，账户名称明确显示“模拟”；不加载真实下单凭据。
  2. D 日盘后拉取并验收数据，冻结数据版本。月末策略生成目标，订单计划最早 D+1 生效。
  3. D+1 到来后，使用当时已获得的状态做事前检查；若状态晚到，只能在到达后采取行动，不能回写成早已知道。
  4. D+1 收盘数据到齐后，模拟器结算此前已冻结的订单：按价格保护、停牌、涨跌停、数量和费用产生模拟成交或拒单。成交价模型沿用主计划的“次日收盘代理”，不能临时挑当天最优价。
  5. 更新持仓、现金、股利权益和可卖数量，核对模拟器与独立账本，生成日报。记录成交所属市场时刻和本系统实际获得/入账时刻。
  6. 没有调仓的日子照样更新估值、处理公司行动、检查风险。下一日继承账户，不能重置为 20 万。

收盘后的完整 bar 只能用于本次模拟结算和之后的策略决策；不能反过来修改此前订单。价格代理与真实人工操作窗口有差异，日报始终显示模拟标记与成交假设。

1.2 模拟器如何复用

PaperAdapter 负责连接持续运行流程与模拟引擎，它不另写一套与回测不同的金融撮合规则。首版优先复用已验证的 RQAlpha 适配层。实际可行的状态续跑方式在 T04 试验后确定：

  • 优先方案：保存并恢复引擎状态、账户、订单、策略状态和事件游标。引擎检查点与 SQLite 事件提交通过 batch_id、状态哈希和运行登记对应；跨文件不假设存在自动原子事务。
  • 备选方案：若该引擎版本不能可靠续跑，从模拟账户起始日重放已冻结的逐日数据、参数和订单。比对既有事件前缀，只把新日事件幂等写入。发现旧交易改变就停止核对，不覆盖昨天已发布的模拟成绩。
  • 两种方案都需要“连续跑十天”和“第五天重启后再跑五天”的等价测试。模拟引擎与审计账本相同不等于独立证明正确，因此仍保留手算案例。

策略/费率升级不能重写过去的模拟结果。首版最容易审计的做法是：继续保留旧 paper 账户，新建独立 paper 账户比较新版本；实际持仓策略切换则显式记录生效日和交接状态。

机器错过某日任务时可以补数据，但未事先生成的订单不能追溯为当天已提交。补做的历史实验归入 research，不能混进前瞻模拟业绩。

4 数据库和存储的备选

组合 适用场景及学习价值 代价与边界 本项目安排
Parquet + DuckDB + SQLite 学习列式数据分析与事务账本的分工；单机日线研究 管理文件 manifest，账户串行写入 首版默认
DuckDB 内部表 + SQLite 学习 SQL 表管理，减少直接处理 Parquet 分区的工作 仍需数据版本和导出；共享写入仍有进程边界 小范围对照实验
SQLite 存行情和账本 很小样本，学习主键、索引、事务和 SQL 大范围分析要测性能；版本化仍要设计；研究与实际账户至少分文件 教学用起点，可保留为 fixtures 后端
PostgreSQL 存行情和账本 学习服务端数据库、多个进程/客户端和事务 需要运行服务、用户权限、索引和备份；行情与账户按 schema/权限隔离 多机或并发需求出现后评估
Parquet + DuckDB + PostgreSQL 保留研究文件层，只升级账户与运行状态服务 三种组件的部署与迁移成本 最自然的后续演进之一
ClickHouse + PostgreSQL 更大规模分钟/逐笔行情分析，账户仍走事务库 明显增加运维；不是目前几个日线策略的必要条件 仅列进阶方向

这些是设计取舍，没有跑过同机基准，不给出虚构性能排名。DuckDB 的本地进程内并发模式、SQLite 的适用边界，以及 PostgreSQL/ClickHouse 的定位可分别核对官方资料。DuckDB · SQLite · PostgreSQL · ClickHouse

兼容性要求：MarketDataStore 对外只暴露按 snapshot、证券、时间查询的接口；LedgerStore 只暴露事务性事件写入和账户读取。策略不能直接写某种数据库 SQL。迁移时先导出事件、检查数量/现金与历史 hash，再切换 writer；不能同时让两个新旧账本各自接单。

DuckDB/SQLite 的嵌入式用法都不需要独立数据库服务器；PostgreSQL 通常需要。数据库品牌变化也不会自动改善数据是否完整或是否有未来信息，这仍属于数据模块。

5 策略和组合方法的备选

策略回答“想持有什么”，组合方法回答“每个标的分多少钱”，风险规则回答“允许这样做吗”。它们分别替换。

策略方向 简单规则示例 新增数据与学习点 主要陷阱
买入持有 / 固定权重 持有预登记 ETF，必要时恢复固定比例 基础行情、分红；学习基准与费用 固定比例调仓和纯买入持有是不同基准
ETF 趋势，首版主线 过去 120 日为正、排序取前二，月度检查 收益窗口、时点、空仓规则 震荡市反复换仓，固定清单的历史选择偏差
ETF 均线趋势 收盘高于过去 N 日均线时持有，否则留现金 学习平滑窗口、信号滞后 参数很多且同一趋势信号高度相关
ETF 相对强弱轮动 在预登记池中持有近期表现较强者 横向排名、换手、持有缓冲 最强者也可能下跌；多个 ETF 持仓重叠
个股低波动，首版主线 在流动性合格池中选择近期波动较小者 历史状态与日收益 集中于某些行业、低波动不等于低亏损
个股动量 从合格池按过去若干月表现排序 学习横截面信号与换手 反转、成本、停牌和不可成交影响
价值 / 质量因子 结合估值、盈利、现金流等排序 必须增加公告时点与历史版本财务数据 最新修订财报回填历史造成未来信息
ML 排名模型 用特征预测未来收益排序，再转目标 Qlib 等、训练/验证切分、模型制品 样本重叠、过拟合、数据漂移，工程复杂度高

以上是研究候选，不是推荐同时实盘运行。趋势与质量的研究动机可参见 Time Series Momentum、Quality Minus Junk；这些论文对象与本项目简化的 A 股长仓规则不同，不把论文业绩移植为本项目预期。

组合分配也有多个学习选项：

  • 固定额度/等权：每个策略或标的使用预设比例，最容易核对，首版使用。
  • 波动率倒数权重：近期波动较小的标的给较大权重；需设单标的上限，不能让低估波动导致极端集中。
  • 风险平价：考虑资产之间相关性，使风险贡献更接近；不等同于简单的波动率倒数。
  • 最小方差或其他约束优化：依赖历史协方差估计及约束；可用 PyPortfolioOpt 或 Riskfolio-Lib。优化器输出连续权重，仍需 Planner 做整手、现金与费用处理，优化无解时进入复核或显式登记的后备方案，不能偷偷去掉约束。

库提供的是组合计算能力，不替你证明收益预测准确。PyPortfolioOpt · Riskfolio-Lib

首版只实现被动基准、ETF 趋势和个股低波动。为了学习新增一条时，只更换 Strategy/Allocator，固定数据、费率、执行政策和评估区间，不用一次实验同时改变五个组件。

6 风控的备选与共同底线

风控不适合简单列成互斥的“A 或 B”。现金不能为负、不可卖数量不能卖、未知委托不能盲目重发、数据过期不能交易等硬检查，任何备选方案都保留。可替换的是组合风险政策和检查器实现。

6.1 可选择的组合风险政策

政策 做法与学习价值 局限 首版安排
固定仓位上限与现金预留 限制总仓位、单只持仓和可用资金 对波动变化反应较少 默认，参数由 paper 示例和实际预算分开
波动率目标 估计近期风险，波动上升时减少目标总仓位 估计滞后，可能在剧烈变动后卖出；默认仍不使用杠杆 后续可加 overlay
回撤分级处理 回撤进入不同区间时预警、暂停加仓或按计划减仓 不能保证损失上限；恢复和滞回规则需要写清 首版有暂停复核，自动减仓另登记
行业/相关性限制 限制同一行业或相关资产集中 需要历史行业和可靠相关性数据；ETF 穿透又需额外数据 数据齐备后再做硬约束
压力测试与尾部风险预算 用极端市场情景检验组合，或研究 CVaR 等约束 历史情景不覆盖所有未来事件，优化也可能不稳定 先做报告；复杂优化后续再加

CVaR 可以理解为：在设定的最差一部分情景里，平均会损失多少。它是统计估计，不是保险。相关组合优化能力见 PyPortfolioOpt 官方文档 与 Riskfolio-Lib 文档。

8 怎样实现兼容而不增加首版负担

接口是兼容性的基础，配置只是选择已实现的组件。下面是待实现的配置示意，不是现在可以直接运行的文件：

mode: paper
data_provider: tushare
market_store: parquet_duckdb
ledger_store: sqlite
engine: rqalpha
execution: paper
strategies:
  - name: etf_trend
    budget: 0.40
  - name: stock_lowvol
    budget: 0.40
risk:
  checks: mandatory_v1
  allocation_policy: fixed_caps
research_runner: local

这些比例仅用于 paper 演示。manual 模式需要独立实际配置。任何一个名字没有实现，启动时明确报 Unsupported，不能配置了 rqdata 就声称已有该适配。

重点边界如下：

DataProvider.fetch(...)                 -> 原始数据批次
MarketDataStore.read(snapshot, asof, ...) -> 标准且时点受限的数据
Strategy.generate(context, data)         -> TargetPortfolio
Allocator.allocate(targets, account)     -> 聚合目标
Planner.plan(target, account, rules)     -> OrderIntent[]
RiskPolicy.evaluate(intents, context)    -> RiskDecision
ExecutionAdapter.publish(intents)        -> 已导出或已提交的状态回报
ExecutionAdapter.collect(...)            -> ExecutionEvent[]
LedgerStore.append_and_project(events)   -> AccountView
ResearchRunner.evaluate(spec)            -> RunResult

publish 的返回状态必须由 adapter 能力决定：人工只是 EXPORTED，模拟器可以产生 SIMULATED_ACK；两者都不是券商真实确认。账户 ledger 带明确命名空间，模拟事件不能导入 manual 账户。

每次替换执行同一套 contract tests：列名、单位、时区、历史可见范围、稳定 ID、事件去重、事务及恢复。不把相同函数签名当作经济语义兼容。

学习顺序建议：

  1. 用 CSV 小样本 + SQLite/Parquet + 买入持有，手算一笔交易。
  2. 接 Tushare 和 DuckDB，比较同一查询的输入输出。
  3. 加 ETF 趋势与个股低波动，保持引擎和费用不变。
  4. 做持续 paper，学习状态、延迟、部分成交和对账。
  5. 替换一个组件做对照：例如 SQLite→PostgreSQL，或等权→波动率倒数。
  6. 有明确研究问题时，再加入 PIT 财报、Qlib 或 AI harness。

只有第一至第四步属于当前主线。第五、六步是可选学习路线，不自动扩大首版实现范围。

本任务包依赖 首版设计、每日操作手册、实现计划 和 模块与备选，面向随后接手实现的 agent。更新日期：2026-10-05。当前只交付规格和调研，不代表已有可运行的投资系统。用户已确定 ETF 与个股首版都要，执行采用人工交易清单与券商记录导入；首版包括持续本地模拟盘，AI harness 尚未选定。备选方案用于后续对照学习，不要求首版全部实现。

  • 复现 1d + next_bar 的行为；用 D 日信号、D+1 突变价格证明实际延迟方案。
  • 核验分红税、分红到账、送转可卖日和退市设置。不能支持的部分列为 adapter 工作。
  • 对 Tushare 每个所需接口探测权限、最早/最晚日期、分页上限、单位与数据覆盖，不在此任务购买服务。
  • 没有 token 时输出 NOT_TESTED，不宣称 source-ready；准备规范 CSV 路径，使后续离线任务可以继续。

完成条件：明确哪些可以复用、哪些需要 Mod，预估适配规模，两个主要资产类别通过最小案例。失败时不以改名为“自研引擎”结束。

T01 工程骨架契约和配置

估计 1–2 人日。产物：pyproject.toml、锁文件、domain/ports、config schema、初始 migration、README。

  • 实现 Instrument、Snapshot、TargetPortfolio、OrderIntent、ExecutionEvent、AccountView、ExperimentSpec。
  • 统一 timestamp、元/股/份、Decimal、稳定 ID、错误码和 schema_version。
  • 支持 demo/research/paper/manual 配置隔离。manual 的券商信息、费率和个人阈值缺失时不能生成可执行清单。
  • 建立数据/引擎/策略/执行 adapter registry，先显式注册类，不做复杂插件市场。
  • 确认 domain 不依赖供应商/框架模块；外部结构导入需要校验。
  • CLI 错误有非零退出码、错误类别和可定位上下文。

完成条件：未知 schema 大版本、无时区 timestamp、NaN/负数量、错误 symbol 映射和非法模式转换可被拒绝。

T02 数据层和快照

估计 3–5 人日。产物：Tushare/CSV adapters、标准表、质量报告、snapshot manifest、数据说明。

  • raw 落盘、断点续传、限流重试、分页完整性和失败批次可恢复；不在调用日志泄漏 token。
  • 转换 vol 手→股/份、amount 千元→元；股票和基金因子分别映射。
  • 把 trade status、company actions、symbols 与行情纳入同一 snapshot。
  • 历史股票范围包括后来退市者；当前列表只是一个数据源，不是历史股票池。
  • published/observed/available 时间分别存储；声明推定可用时间与严格观测模式。
  • 分红采用已实施方案，税前金额与税后字段分清，不能重复扣税。
  • 发布前校验，生成内容哈希；重拉修订产生新快照，旧快照不变。
  • 校验跨供应商替换：同一规范 CSV 的数据经过不同适配器，标准表一致；真实两供应商比较只能在具备权限后做。

完成条件：断点/重复拉取不漏行不重复；缺关键数据阻断发布；旧 snapshot 重放不受新数据改变；股票全市场研究与抽样 demo 可区分。

T03 事件账本和公司行动

估计 3–5 人日。产物：SQLite migration、事件去重、持仓批次/现金投影、手算 fixtures。

  • 先做资金、成交、费用和冻结；然后实现应收股利、到账、红利税、送转/解锁、退市估值、实际回收。
  • 事务内完成事件与投影；把 raw/source 证据与已入账事件关联。
  • 重放不依赖当前墙上时间、当前供应商或随机数。
  • 更正走 reversal/correction；批次税务信息不足时显式标记，不伪造日期。
  • 持仓可卖、现金可用/总额、未结订单预留清晰分开。

完成条件：实现计划第 8 节的手算结果精确一致；同源重复事件不影响账户；重建账本与原状态逐项一致。

T04 RQAlpha 适配和受限回测

估计 3–5 人日。产物：CanonicalDataSource、策略桥接器、成交/公司行动事件转换、引擎差异报告。

  • 仅从指定 snapshot 取数据；默认 bundle 只用于独立 smoke test。
  • 先缓存 D 目标，到 D+1 日终执行；禁止 signal callback 访问 D+1 bar。
  • Planner/风险共用；买入不使用同日卖出资金；未完成目标按登记政策延续。
  • 配置税费/滑点/涨跌停/量限制；锁定实际引擎版本和有效参数，保存 requested/effective 两份配置。
  • 核验引擎股利税、送转、退市与标准账本的差异，必要时用 Mod 修正。
  • 在 5–10 日合成路径上逐笔、逐日比较独立账本和引擎账户；不是只比最终收益。
  • 验证 paper 跨日状态恢复；若需重放，则冻结每日输入与订单并验证已有事件前缀。检查点与账本提交中断后能恢复，不能重复入账或改写已发布的模拟记录。

完成条件：时点突变、T+1、费用、公司行动、受限成交全部通过；不支持的事件使 run 为 INVALID，不能输出可发布业绩。

T05 组合规划和四层风控

估计 2–3 人日。产物：allocator、planner、risk decisions、暂停/恢复命令。

  • ETF 和股票各自目标先聚合，费用和现金在账户层约束；基准可单独配置。
  • 目标差额扣除已登记未完成订单；整手取整后复核限价与费用。
  • 风险规则只能返回有解释的通过/阻断/复核，所有缩量都生成新计划。
  • 实现数据不齐、流动性不足、重复委托、账户未知、阈值超限、恢复流程。
  • 机器故障、净值风险和主动减仓的处置不要混成“全部市价清仓”。

完成条件：每项约束有反例测试；两个策略同时想买入时不能超用现金；暂停后重启仍暂停；对账未通过时不发布新买单。

T06 人工订单和导入对账

估计 2–4 人日。产物：plan.json/csv/html、broker mapping、四类 CSV importer、对账报告。

  • 把导出、人工提交、券商确认、成交、撤单和未知状态区分。
  • 通用 CSV + 一种实际券商格式；没有真实样例先保留待映射状态。
  • import preview → 原子 apply；成交编号作用域和重复导出测试。
  • 部分成交/晚到费用/计划外交易/未知订单/撤单期间成交都入事件账本。
  • 同一输入重复导出同一 plan；账户变化生成新版本，旧清单明确作废。
  • 导入 orders、fills、cash_movements 和 account_snapshot 后统一核对。

完成条件：操作人按 README 演练一次计划与两次部分成交导入；重复导入不重复计账，未知订单不会生成替代买单，三方差异可追踪到原始行。

T07 两条策略和研究基准

估计 1–2 人日。产物：两个纯策略、被动基准、预登记参数、正式实验配置。

  • 实现 ETF 120 日正趋势前二与股票流动性前 300、60 日低波动前五。
  • 覆盖不足窗口、非调仓日、空池、并列排序、退市历史、资金不足一手。
  • 所有参数显式配置，策略不直接访问外部网络和数据库。
  • 使用真实全量可投资历史做正式研究；固定 ETF 清单的条件选择偏差写入报告。
  • 压力成本、延迟、小本金情景只评价预登记变化，不自动“找最优”。

完成条件：相同输入输出一致；改变 D+1 数据不改变 D 信号；新增策略仅实现同一契约可执行。

T08 运行记录评估与报告

估计 1–2 人日，可先定义产物 schema。产物：manifest、metrics、HTML、实验索引。

  • 每个 run 记录 snapshot、代码、依赖、费率、规则、风险、策略、初始账户和执行政策。
  • 报告区分合成/真实历史/paper/manual，显示代理成交和全部限制。
  • 保存失败实验，封存集独立权限；研究进程不能因为拿到路径就读封存数据。
  • 统一净值、资金流、换手和基准定义；费用分别显示。
  • 输出未来 harness 的 evaluate 入口，首版不接 LLM 自动下单。

完成条件：任意一个报告可追溯并重放；改费率或 snapshot 后不会误命中旧缓存；报告无虚构成交/收益。

T09 定时运行备份与集成故障

估计 2–3 人日。产物：daily CLI、OS 调度例子、备份恢复 runbook、集成证据。

  • 日历驱动，锁与幂等 job，数据未齐/错过时间产生清晰状态。
  • 本地账户单写者，研究并发隔离，备份调用一致性 API。
  • 注入进程中断、导入中断、磁盘不足、manifest 未发布、重复任务和晚到回报。
  • 从备份重建并重放源文件，核对计划/事件/现金/持仓。
  • 完成离线 demo 一条命令以及真实数据端到端用例。
  • 增加持续 paper 的重复日运行、重启、历史数据修订和错过调仓日演练；事后生成的订单不能混入前瞻模拟成绩。
  • 实现 daily run、status 和最新日报入口；严格先结算旧事实并对账，再产生未来目标。状态区分任务缺失、数据等待、交割待确认和休市，不让昨日成功页面掩盖今日故障。

完成条件：无重复资金影响、无错误计划自动补发；恢复步骤由未参与实现的操作者也能照做。

T10 持续 paper 和交接

时间取决于市场日历。产物：连续运行日志、调仓演练、已知限制、启用人工账户清单。

  • 真实新数据逐日进入，跨周末/假期正确处理。
  • 至少演练两个策略共同调仓、部分成交、一次未知委托和一次恢复。
  • 更新用户券商导出映射和实际费率，核实报告义务，初始化账户/风险配置。
  • 策略审批和系统审批分开记录；可以交付稳定系统但不建议启用主动策略。
  • 按每日操作手册演练普通日、D/D+1/D+2 调仓、交割单晚到、错过执行窗口和异常恢复；用户无需读源代码即可判断下一步。

完成条件：README、数据字典、ADR、命令和输出路径可独立使用；未实测部分逐项列出，不以“基本完成”遮盖。

4 数据调研的新结论

Tushare 对首版价格类策略值得优先试验，但“API 存在”不能替代历史全覆盖验收。该选择基于公开接口、预算和你较强的 Python 能力；若整理历史状态耗时很高，付费使用更完整数据可能更划算。

值得特别注意的官方字段：

  • daily 的 pre_close 标注为除权参考昨收，不能直接等同上一行未复权 close；vol 是手、amount 是千元；当前文档还提供盘后成交量/额字段。应确认总量与盘后量的包含关系，不能重复相加。股票日线
  • dividend 同时提供 cash_div（税后）与 cash_div_tax（税前），并区分 ex_date、pay_date、div_listdate。采用税前值再按账户计算税时，不得误用税后值重复扣税；每日更新时段写为 20–21 点，日常任务应等待相关数据齐备。分红送股
  • bak_basic 文档起点为 2016 年；其中包含的财务衍生字段不能因为与历史日期同表就自动视为完整 PIT 财报。股票历史列表
  • stock_st 按日期提供历史列表，但提醒过早历史无法补齐，并给出约 09:20 的当日更新时间。历史查询能力与真正保留全部公告修订仍是两回事。ST 列表
  • etf_limit 已有独立接口，不必机械把股票涨跌停接口套到所有 ETF；历史起点和终止上市 ETF 覆盖仍需 probe。ETF 限价

RQData 的 get_pit_financials_ex 带 date 与 statements，可用于按查询时点和报表版本取值；这为后续质量/价值因子提供更合适的调查入口。具体数据覆盖、授权与报价尚未验证。RQData

AKShare 继续适合抽样核对或学习；本轮不建议它成为关键实盘数据唯一来源。免费源可以有用，关键是失败/修订/单位/许可有明确边界，而不是把“免费”当稳定性承诺。

个人数据预算建议拆成三个情景而非先花满：已有机器 + 日线试验约按官方 500–1,000 元年费档探测；PIT/更完整服务询价后再决定；分钟数据仅在执行误差妨碍判断时购买所需范围。首版人工执行无需先买 Windows 机器。20 万本金上每年 3,000 元固定费相当于 1.5%，应单独显示。

5 为什么是 Parquet DuckDB SQLite

本项目选型的依据是访问模式：行情和因子是批量扫描、可重建，账户是小量事务、必须可靠。前者使用列式文件，后者使用事务库。不需要把所有东西塞进同一种数据库。

DuckDB 的本地进程内模式有单进程写入边界；官方也介绍新的多进程方案，但个人日线首版没有引入其复杂度的收益。SQLite WAL 允许读写协作但一次仅一个写者，且要求同机共享内存。本设计因此将研究并行与账户写入分离。DuckDB · SQLite

迁移前后收益差异需要解释，不以“接口能调用”作为兼容成功；例如公司行动、收盘时间和费率口径的变化都可能改变结果。

8 交易接入的后续路线

当前用户选择人工执行，所以首版只研究自动接入边界，不开通或连接账户。xtquant 官方文档提供报撤单、资产/持仓/订单/成交查询及回调，这与标准 ExecutionAdapter 的未来实现相符。迅投官方文档

SDK 的异步请求序号、券商委托编号和本系统 intent_id 是不同对象；网络超时无法天然保证 exactly-once。未来自动接入必须保留本地意图→提交→查询确认→未知恢复流程，不能调用异常就再次下单。通过 vn.py 接 gateway 也一样。

是否支持 Mac/Windows、账户资产门槛、模拟环境、ETF 委托类型和当前 SDK 版本要向实际券商确认。不要因为网上存在 Python 示例就把这些条件视为满足。
